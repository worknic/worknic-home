# 운영 연결

## 호스팅 구조

공식 홈페이지의 정적 호스팅을 유지하고, 주문 서비스는 별도의 Node.js 24 서버에서 운영합니다. 고객용 HTTPS 주소를 확정해야 합니다. 이 코드의 고객·관리·API는 **같은 출처**에서 제공해야 하며 CORS를 열지 않습니다. 별도 주문 서브도메인 또는 공식 도메인의 `/trade/*`, `/api/trade/*`를 서버로 연결하는 리버스 프록시를 사용할 수 있습니다. 서브도메인은 실제 DNS와 기존 서비스 사용 여부를 확인한 후 정합니다.

구매자 개인정보·세션·주문은 서버의 SQLite DB에 저장됩니다. 영속 볼륨이 없는 서버리스 실행 환경이나 GitHub Pages만으로 운영할 수 없습니다. 최초 구성은 단일 서버·단일 프로세스입니다. 여러 서버로 확장할 때는 공유 데이터베이스로 이전해야 합니다.

## 서버 환경변수

| 변수 | 설정 |
| --- | --- |
| `NODE_ENV` | 운영은 `production` |
| `TRADE_ORIGIN` | 고객이 사용하는 HTTPS 출처. 경로 없이 지정 |
| `TRADE_DATA_DIR` | 영속 디스크의 비공개 DB 디렉터리. 웹 문서 루트 밖 |
| `TRADE_ADMIN_TOTP_SECRET` | 인증 앱용 base32 시크릿 32자 이상. 서버 비밀 설정으로 등록 |
| `HOST` | 직접 실행 기본값 `127.0.0.1`, 컨테이너는 `0.0.0.0` |
| `PORT` | 기본 `8080` |
| `TRADE_TRUST_PROXY` | 신뢰 가능한 프록시가 X-Forwarded-For를 덮어쓰는 환경에서만 `1` |

시크릿은 채팅·저장소·명령 인수에 넣지 않습니다. 운영은 HTTPS·영속 디스크·관리자 OTP 설정이 없으면 시작을 거부합니다. 담당자는 암호에 더해 인증 앱 코드로 로그인합니다. 운영 서버의 인증 앱 시크릿을 관리자에게 안전하게 전달하고 복구 절차를 보관하세요.

Dockerfile의 빌드 컨텍스트는 저장소 루트입니다.

```sh
docker build -f trade/Dockerfile -t worknic-trade .
```

실행 시 `/data`를 영속 볼륨에 연결하고 UID 1000이 쓰기 가능하도록 설정합니다. 호스팅의 비밀 설정으로 위 환경변수를 주입합니다. 최초 관리자 생성은 같은 환경·볼륨에서 `node trade/server/admin.mjs`를 실행합니다. 애플리케이션은 비밀번호를 저장할 때 scrypt 해시와 개별 salt를 사용합니다. 기존 Google Apps Script 관리자 비밀번호나 토큰을 복사하지 않습니다.

## 운영 시작 순서

1. HTTPS 서버·영속 디스크·백업 연결, 관리자 생성 및 OTP 등록.
2. 담당자 화면의 입금계좌와 배송·포장비를 대조. 초기 설정은 하나은행 556-910020-91004, 워크닉 주식회사 / 50만원 미만 5천원, 이상 무료.
3. 상품별 부가세 포함 단가·주문 가능 수량·별도 배송 여부 검토. 카탈로그에는 가격을 추정해 채우지 않습니다.
4. `trade/index.html`의 회원가입 개인정보 안내와 공식 `/privacy/`, `/terms/`에 실제 주문·배송 처리, 보관·파기, 취소·환불, 수탁업체 등 운영 내용을 일치시킵니다. 실제 운영 정책을 확정한 뒤 배포합니다.
5. 검증용 사업자 계정으로 승인·주문·명세서·입금 확인·발송을 확인. 은행으로 실제 송금할 필요는 없습니다. 검증 내역은 운영 주문과 구분해 관리합니다.
6. 운영 접수를 열고 공식 홈페이지의 상품·사업자 메뉴에서 고객 주소를 연결합니다. 기존 가입 신청은 당분간 유지하고, 기존 신청자의 비밀번호를 임의로 만들거나 평문으로 이관하지 않습니다.

## 카탈로그 동기화

최초 설치 시 배포된 `data/catalog.json`을 가져옵니다. 이후 기존 브랜드 관리 화면에서 상품을 추가·수정·공개한 뒤, 주문 관리 화면의 **브랜드 관리 상품 불러오기**를 누르면 기존 공개 카탈로그 API에서 이름·사진·모델과 공개 여부를 동기화합니다. 신규 상품의 단가·수량·주문 가능 여부는 담당자가 설정합니다. 기존 단가·재고는 유지하며 숨긴 상품은 주문 불가로 전환하고 기존 주문 스냅샷은 보존합니다. 서버 재시작 시 동기화한 정보를 과거 배포 파일로 덮어쓰지 않습니다.

관리자 세션이 있어야 동기화를 실행할 수 있고, 고정된 기존 공개 카탈로그 읽기 작업만 호출합니다. 실패·잘못된 형식은 저장하지 않습니다. 가격·수량·주문 승인·입금·발송은 담당자 웹 화면에서 관리할 수 있어 일상적인 상품 추가와 주문 처리에 코드 수정이 필요하지 않습니다.

## 백업·복구

SQLite WAL을 사용하므로 운영 중 `trade.sqlite` 파일만 복사하지 않습니다. SQLite 온라인 백업 또는 서버를 안전하게 정지한 뒤 DB·WAL을 함께 백업합니다. 백업은 별도 비공개 저장소에 암호화 보관하고 복구 테스트를 수행합니다. 세션·재설정 토큰은 DB에서 해시로만 보관하며, DB·백업은 Git에 커밋하지 않습니다.

입금기한 만료는 1분 간격 및 주문 조회 시 처리합니다. 실패는 서버 로그의 `Order expiry failed`로 식별합니다. 주문·가격·승인·설정 변경은 `audit` 테이블에 담당자와 시간을 기록합니다. 단일 SQLite 파일의 보존·접근 권한은 운영자가 관리합니다. 회원 탈퇴·법정 보관기간 종료에 따른 삭제·분리 보관과 유료 주문의 환불은 운영 절차로 처리하며 자동화는 후속 범위입니다.
